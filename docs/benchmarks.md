# Benchmarks

> 逐周期实测数据：Release 构建、同一工具链与镜像布局。每个用例的 `result` =
> 停机时架构寄存器 x10 的低 8 位，`cycles` 为包含 HALT 后存储系统排空的端到端总周期数；
> `ipc-cycles` 冻结在 HALT 实际提交周期（包含该周期），`retired` 为 ROB 实际退休的架构指令数，
> `IPC = retired / ipc-cycles`。
>
> ⚠️ **`cycles` 与 `runtime(s)` 的构建口径不同，不可混用**：`cycles` 是架构无关的
> 周期计数，取自本表自身；`runtime(s)` 是**宿主机墙钟**，取自**原生 Windows/MinGW**
> 构建（根 `test.sh` 口径）—— 实测其量级（array_test1 约 11 ms）低于 WSL ELF 的
> 进程启动地板（实测 12–18 ms），故不可能是 WSL 构建。下节 RV32M A/B 表中的
> `M time(s)` / `I time(s)` 则取自 **WSL ELF**（`test_M.sh` 口径），两处时间列
> **不同源、不可相互比较**。
>
> **本表是行为结果与测量数据的单一记录源**（`data/golden/` 已废弃删除）：根 `test.sh`、
> `RISC-V-Simulator-Template/test.sh` 与根目录 `test_M.sh` 按列名读取 `result` 和 `cycles`，
> 路径可用环境变量 `GOLDEN_MD` 覆盖。当前两份 `test.sh` 的通过门禁是进程未崩溃、
> IPC 统计有效且 `result`（x10）匹配；`cycles` 会被读取、打印和汇总，但只作为记录/参考数据，
> 脚本并不与表中值比较。需要逐周期等价时必须另行显式对比 clock。
>
> **HALT 口径**：课程终止字 `0x0ff00513` 在 issue 阶段被模拟器特殊处理为立即就绪的终止标记，
> 不执行其编码对应的 `addi` 语义，因此不计入 `retired`；但它的提交周期计入 `ipc-cycles`。
> CPU 在周期前后观察 ROB 的 7-bit head 与 haltCommitted：head 环形差值即实际 pop 数，
> haltCommitted 的 0→1 跃迁标记 HALT 提交；不修改 ROB 接口，也不复制提交条件。TOTAL IPC 一律使用
> `Σretired / Σipc-cycles`，不是逐用例 IPC 的算术平均。

## Constraints

- Main memory latency is fixed at **20 cycles**（取指侧 IMEM 缺失回填与数据侧 DCache
  缺失回填共用该延迟）。
- No L1 cache hit latency：ICache 命中当拍组包、DCache 命中 1 拍自答（store 当场落行）。
- L1 cache：指令缓存 **8 KB**（512×16 B，直接映射）+ 数据缓存 **64 KB**（1024 组×4 路×16 B，
  写回 + 写分配，tree-PLRU）。D$-% 覆盖 load 与 store 的全部访存访问。
- 预测准确率按控制流类型拆分：**cond** = 条件分支（BRU 解析，方向+目标）；
  **jal** = 直接跳转（JAL，ALU 结果总线）；**jalr** = 间接跳转（JALR）；
  **branch** = 三者汇总的整体准确率（与 README 口径一致）。

取数命令（WSL ELF 构建，逐用例）：

```bash
VERBOSE=branch,clock,icache,dcache <bin> < data/testcases/<case>.data >/dev/null
# clock: 1184
# ipc: 0.355030 retired=420 cycles=1183
# branch: 111/175 correct (63.43%)
# branch-type: cond=84/124(67.74%) jal=19/27(70.37%) jalr=8/24(33.33%)
# icache: hits=638 misses=122 total=760 hit-rate=83.95%
# dcache: hits=30 misses=5 total=35 hit-rate=85.71%
```

> 逐列取数口径：`cond-%` / `jal-%` / `jalr-%` / `branch-%` 由**命中分数**换算
> （`correct/total × 100`，最多 4 位小数、去尾零；分母为 0 记 `0`），
> `I$-%` / `D$-%` 直接取对应行的 `hit-rate`（固定 2 位小数）。
> `result` = 停机 x10 低 8 位；`cycles` = 端到端总周期；`ipc-cycles` = HALT 提交周期；
> `retired` = 排除 HALT 标记后的实际 ROB 退休数；`IPC = retired / ipc-cycles`（保留 6 位小数）。


## RV32M A/B（硬件乘除法收益实测）

> 统一双臂 A/B 语料（`data/testcases_rv32im/`）：
> **M 臂** = `-march=rv32im`（乘法 `mul/mulh/...` 与除法 `div/divu/rem/remu` 全部内联为硬件单元，
> 链接行去掉 `libdiv.S`）；**I 臂** = `-march=rv32i` + `libdiv.S`（软例程 `__mulsi3` 负责 `*`、软除法例程负责 `/` 与 `%`）。
> 两臂同 `crt0` / 同链接脚本 / 同 `-O1`（避 `magic.c` 的 `-O2` UB），故 clock 差即**纯 M 扩展（乘+除）收益**；
> **实际运行时间**由 `test_M.sh` 直接执行模拟器二进制、以 `date +%s%N` 测墙钟得到（同一次运行内两臂同口径）。
> `x10` 两臂一致即视为通过；`x10` 另对照主表 `result` 列（课程原镜像口径，自制镜像 layout 不同，仅比 x10）。
> 两臂编译出的动态指令流不同，因此 M/I 的 IPC 可以分别评价各自流水线利用率，但**不可把 IPC 比值当作性能加速比**；
> 工作负载加速仍看同一 case 的 `I clock / M clock`。

### 读法

- **收益与乘/除的动态占比正相关**：`pi`（除法占周期 99%+）提速 **17.601×**（约 1.38 亿 → 782 万周期）；
  `gcd`/`manyarguments`/`lvalue2`/`basicopt1`/`expr` 等除法位于热循环，提速 **1.87–3.44×**；
  `statement_test` 乘法集中（3 条静态 `mul`），提速 **2.241×**。
- **阴性对照**：`naive` 无 `mul`/`div`（静态条数 0/0），M/I 双臂 clock 逐拍相同（93）；`qsort`/`tak`/`magic` 仅 1 条
  `div/rem` 且不在热路径，clock 几乎不动（Δclock ≈ 0）——证明收益完全来自硬件乘/除单元。
- **`magic` 的 Δclock≈0 是真实结果**：其唯一 `div` 位于数据相关循环，硬件 SRT 与软 `libdiv.S` 在该用例的
  实际延迟接近，故收益被其余工作稀释；`pi` 的同类 `div` 因量级巨大才显出 17× 收益。
- **跨臂 brAcc 不可直接比较**：两臂编译出的代码不同，软例程自带大量分支（如 `gcd` 的 M 臂仅 7 次分支、
  I 臂 125 次），准确率差反映**代码差异**而非预测器退化；预测器回归仍以「同一镜像跨模拟器版本」对主表四列为准
  （2026-09-18 复核：18/18 x10 全对）。
